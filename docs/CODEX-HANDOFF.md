日期：2026-10-26｜当前任务：**接着已有真实核心推进 Windows 系统输入法，连续执行到可日用的安装包。**

## 1. 直接开始执行

你接手的工程已有代码、真实词库与测试，不是空白规划项目。先阅读现有内容并确认当前环境，然后实施下一项未完成的平台工作。不要重新起名、重写整份规划、只画键盘外观，也不要用网页键盘或自建文本框替代 Windows 系统输入法。

用户已确定：PC和手机都要，支持五笔与拼音，官方版本免费、开源、无广告、不采集用户信息，由用户持续维护。当前工作名称为“言舟 · YANVY”。Windows优先做到日用，Android和iOS按原生系统继续开发。

普通实现、可逆修改、内部构建和必要验证持续执行，不要求用户逐步骤确认。仅在真正需要账号、签名凭据、付费、超出现有授权的权限或不可逆操作时明确指出具体需要；先完成不受该条件影响的工作。

## 3. 首要实施顺序：Windows

### A. 搭好真实Windows构建

1. 核实Windows执行环境、Visual Studio C++工具链、SDK与librime运行库。没有真实Windows时，先完成可进行的源码、构建配置与静态核对，并精确记录尚未运行的步骤；不能把Linux通过或交叉编译当成Windows使用通过。
2. 用现有CMake入口编译核心，修正Windows文件路径、字符编码、DLL加载与运行库部署。锁定使用的依赖版本。
3. 将当前五笔86、全拼和必要反查依赖作为随包离线数据；正式运行不下载组件。维护原有许可证与哈希清单。

### B. 接入TSF与候选窗

4. 优先复用审查后的小狼毫Weasel原生接入代码，固定上游提交并保留GPL许可和历史来源；不要重新实现成熟的系统输入机制。具体构建产物按真实复制、链接与衍生关系整理许可。
5. 接入注册、激活、键盘事件、组合串、候选、提交、取消、焦点切换和停用流程。调用已有核心能力，或在必要架构调整后继续保留已验证的策略和数据。
6. 实现跟随输入位置的候选窗和“中/英、五/拼”状态；图标从当前母版生成平台资源。不要以全局键盘钩子、模拟粘贴、浏览器脚本或剪贴板轮询替代TSF。
7. 每次引擎或候选初始化失败，保持原应用可用并允许切回系统输入法，不吞掉整段键盘输入。

### C. 补足日用流程

8. 实现数字选词、翻页、空格、Esc、Enter、退格、未完成组合串的编辑和方案切换。当前切换方案取消未完成输入且不提交，该行为若调整必须记录理由与测试。
9. 分别处理五笔四码唯一候选上屏与下一键顶屏；保持重码顺序可预期。首版以五笔86为工作假设，不宣称用户指定过86版。
10. 增加真正的拼音短语、长句、分段选词和混排测试；不要把既有少量词语断言包装成输入质量达标。先全拼，九宫格留在手机后续阶段。
11. 完成本地设置、深浅色、字号、候选数和必要按键选项。正式默认无自动学习、无输入历史、无剪贴板历史。

### D. 安装与交付

12. 形成实际Windows安装包，验证干净安装、系统启用、升级和卸载。不得强改默认输入法；卸载后系统仍有可用输入方式。
13. 在真实Windows中验证记事本类控件、浏览器、Word/WPS、聊天应用及至少一个32位应用，记录环境版本和实际结果。
14. 对最终发布构建复核依赖、权限、文件写入及网络行为，给出安装包SHA-256、对应源码提交和已知限制。
15. Windows日用关口通过后继续推进Android、iOS；没有完成的平台明确写“未完成/未运行”，不虚报“全平台已交付”。

Windows技术依据：[Microsoft IME要求](https://learn.microsoft.com/en-us/windows/apps/develop/input/input-method-editor-requirements)、[Weasel原始仓库](https://github.com/rime/weasel)、[librime原始仓库](https://github.com/rime/librime)。

## 4. 隐私约束必须延续到平台层

- 默认不学习，首版不提供隐式学习路径。保留已修复的命名 translator 等绕过反例，延续受信任文件清单及实际生效配置、组件检查，而非只信任默认三个布尔值。创建会话前的策略检查不能因“先跑通”而删除或绕过。
- 不接入广告、统计、崩溃正文上传、账号、设备追踪、云候选或后台更新检查。
- 不自动读取剪贴板、通讯录或文档，不保存按键串、提交内容、周边文本或候选日志。
- 不把诊断CLI标准输出重定向成正式产品日志。反馈仅使用用户主动提供并可检查的最小错误信息。
- 当前固定离线方案不支持任意用户配置、Lua、脚本、命令或远程配置；默认执行信任清单检查。后续本地设置应提供受限选项，并验证与这一策略兼容；词库与皮肤导入另行设计，不自动执行其携带代码。
- 保留必要配置与编译词典不等于记录输入；报告写清真实文件类型，不能笼统宣称零写盘。
- 网络验证覆盖正式构建的初次运行、输入、切换、空闲和升级后运行。记录观察范围；信任清单不是沙盒，不宣称能隔离恶意操作系统或控制接收文字的其他应用。

当前默认无学习测试仍须保留；新增测试针对系统接入造成的新风险，例如失焦误提交、重复上屏、窗口串字、崩溃后的文本残留和配置回退。不要为文案或纯外观微调增加镜像式测试，也不要在充分验证后反复扩大无关测试。

## 5. 手机延续规则

Android使用Kotlin原生`InputMethodService`，必要时以JNI连接公共核心；若采用同文则保留引入部分的许可。首批26键全拼、五笔86、英文/数字/符号，再单独完成九宫格消歧和编辑。发布构建检查合并Manifest无`INTERNET`、没有输入内容经外部组件传递、没有正文自动备份。来源：[Android官方开发指南](https://developer.android.com/develop/ui/views/touch-and-input/creating-input-method)、[Trime](https://github.com/osfans/trime)。

iOS使用Swift原生键盘扩展，保持`RequestsOpenAccess=false`。内置词库和基本输入不得依赖完全访问；容器App配置与扩展沙盒边界先实测。密码框等系统接管场景遵循平台机制。不能未经许可检查就把GPL前端复制到iOS并承诺App Store可上架。来源：[Apple开放访问说明](https://developer.apple.com/documentation/uikit/configuring-open-access-for-a-custom-keyboard)、[键盘扩展文档](https://developer.apple.com/library/archive/documentation/General/Conceptual/ExtensibilityPG/CustomKeyboard.html)、[开发者分发协议](https://developer.apple.com/support/terms/apple-developer-program-license-agreement/)。
